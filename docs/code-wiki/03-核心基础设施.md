# 03 · 核心基础设施（PCL.Core）

`PCL.Core` 是整个项目的底座，负责“非业务、可复用”的能力：生命周期、依赖注入、配置、日志、事件、数据库、命令行、本地化，以及大量的 IO/网络/Minecraft 基础模型。本章聚焦 `PCL.Core/App`、`PCL.Core/Logging`、`PCL.Core/ViewModel` 等应用级基础设施；IO 与 Minecraft 见后续章节。

## 1. 目录速览

```text
PCL.Core/App
├── Basics.cs                 # 全局静态基础方法
├── Config.cs                 # 全局配置项（由源生成器生成访问器）
├── Metadata.cs               # 启动器元数据模型
├── Paths.cs                  # 数据目录解析
├── Secrets.cs                # 敏感配置/环境变量
├── States.cs                 # 运行期全局状态（如当前语言）
├── Cli/                      # 命令行解析
├── Configuration/            # 配置系统
├── Database/                 # LiteDB 数据库服务
├── Essentials/               # 应用级服务（单例、更新、RPC、遥测等）
├── EventBus/                 # 事件总线
├── IoC/                      # 生命周期与 DI
└── Localization/             # 本地化核心
```

## 2. IoC 与生命周期

### 2.1 类型与职责

| 类型 | 职责 |
|---|---|
| `Lifecycle` | 全局生命周期入口：初始化、状态推进、服务注册/启停、退出 |
| `LifecycleState` | 生命周期状态枚举 |
| `LifecycleContext` | 单个服务的上下文：日志、退出请求、异常处理 |
| `ILifecycleService` | 生命周期服务契约 |
| `LifecycleServiceAttribute` | 声明服务所属状态与优先级 |
| `LifecycleScopeAttribute` | 源生成器据此自动实现 `ILifecycleService` |
| `LifecycleStartAttribute` / `LifecycleStopAttribute` | 标记启动/停止方法 |
| `LifecycleLogs` | 生命周期专用日志适配 |
| `LifecycleServiceTypes`（生成） | 所有生命周期服务的类型清单 |

### 2.2 服务契约

```csharp
public interface ILifecycleService
{
    string Identifier { get; }
    string Name { get; }
    bool SupportAsync { get; }

    Task StartAsync(LifecycleContext context);
    Task StopAsync(LifecycleContext context);
}
```

推荐写法是“静态 + Scope”：

```csharp
[LifecycleService(LifecycleState.Running, Priority = 100)]
[LifecycleScope("update-check", "检查更新", asyncStart: true)]
public sealed partial class UpdateService
{
    [LifecycleStart]
    private static async Task _StartAsync(LifecycleContext context)
    {
        // 真实实现
    }

    [LifecycleStop]
    private static Task _StopAsync(LifecycleContext context)
    {
        // 真实实现
    }
}
```

`LifecycleScopeGenerator` 会生成一份 `partial` 类，实现 `ILifecycleService`，把静态方法转成实例生命周期；`LifecycleServiceTypesGenerator` 汇总出 `LifecycleServiceTypes.GetServiceTypes(state)`，供 `Lifecycle` 按状态发现服务。

### 2.3 状态推进

| 方法 | 触发时机 |
|---|---|
| `Lifecycle.OnInitialize()` | `Program.Main` 末尾，启动 `BeforeLoading` |
| `Lifecycle.OnLoading()` | 日志与配置就绪、主窗体创建前；推进 `Loading → WindowCreating` |
| `Lifecycle.OnWindowCreated()` | 主窗体加载完成；推进 `WindowCreated`，并在后台线程进入 `Running` |
| `Lifecycle.Shutdown()` / `ForceShutdown()` | 正常/强制退出，执行 `Exiting` |
| `Lifecycle.StartService/StopService` | 手动启停 `Manual` 服务 |

补充规则：

- `Lifecycle.ServiceState` 与 `CurrentState` 用于查询当前进度。
- `Lifecycle.RequestRestartOnExit` 让退出后自动重启（用于更新、语言切换等）。
- `LifecycleContext.RequestExit()` 支持带错误码退出。
- 所有状态转换都带日志，便于排查启动挂起。

### 2.4 注册与实例化

- `Lifecycle` 通过生成的 `LifecycleServiceTypes.GetServiceTypes(state)` 反射创建实例。
- 使用 `Activator.CreateInstance` 前会检查无参构造。
- 服务实例按 `Identifier` 去重；重复注册会记录警告。
- `Manual` 服务在 `OnInitialize` 中提前实例化，但不自动启动。

### 2.5 与 DI 的关系

生命周期负责“启动顺序与开关”，DI（`Microsoft.Extensions.DependencyInjection`）负责“对象构造与依赖图”。两者在组合根处汇合：

- `LauncherServiceRegistration` 构建容器；
- `ApplicationRuntime` 保存 `IServiceProvider`；
- 生命周期服务通过 `ApplicationRuntime.GetRequiredService<T>()` 获取依赖；
- 架构测试会校验服务注册是否完整。

## 3. 配置系统

配置系统由“声明式属性 + 多来源存储 + 缓存 + 事件/观察者 + 迁移”组成。

### 3.1 声明方式

```csharp
public static partial class Config
{
    [ConfigGroup("Network")]
    partial class NetworkConfigGroup
    {
        [ConfigItem<bool>("SystemNetEnableDoH", true)]
        public partial bool EnableDoH { get; set; }

        [ConfigItem<string>("SystemHttpProxy", "", ConfigSource.SharedEncrypt)]
        public partial string CustomAddress { get; set; }
    }
}
```

- `[ConfigItem<T>(key, default, source)]`：值类型默认值可直接写在特性里。
- `[AnyConfigItem<T>(key, source)]`：复杂类型默认值通过无参构造器创建。
- `[ConfigGroup(name, source)]`：命名作用域，可嵌套。
- `[RegisterConfigEvent]`：把静态 `ConfigEventRegistry` 属性注册为事件观察器。
- 属性必须是 `partial`，由 `ConfigGenerator` 生成 getter/setter 与 `ConfigItem<T>` 实例。

### 3.2 配置来源

`ConfigSource`：

| 值 | 存储位置 | 格式 |
|---|---|---|
| `Shared` | `Paths.SharedData/config.v1.json` | JSON |
| `SharedEncrypt` | 共享加密配置 | 加密 JSON |
| `Local` | `Paths.Data/config.v1.yml` | YAML |
| `GameInstance` | `<实例目录>/PCL/config.v1.yml` | YAML |

相关类型：

- `ConfigService`：静态服务，管理所有 `ConfigItem`、键集合、Provider、迁移。
- `IConfigProvider` / `ConfigStorage`：读写抽象。
- `JsonFileProvider`、`YamlFileProvider`、`EncryptedFileConfigStorage`、`MemoryFileProvider`、`DynamicCacheConfigStorage`。
- `ConfigValueCache<TValue>`：按 `argument`（如实例路径）缓存值。
- `ConfigEvent`：`Get/Set/Reset/Changed/CheckDefault` 等事件位标志。
- `ConfigObserver` / `ConfigEventArgs`：可拦截、取消、替换新值的观察者模型。
- `ConfigMigration`：版本迁移（`SharedVersion` / `LocalVersion`）。
- `ArgConfig`：以 `argument` 区分上下文的配置（典型是实例级配置）。

### 3.3 读取与写入

```csharp
bool enableDoH = Config.Network.EnableDoH;
Config.Network.EnableDoH = false;

// 非泛型/动态访问
ConfigService.TrySetValue("SystemNetEnableDoH", true);
if (ConfigService.TryGetConfigItem<int>("SystemMaxLog", out var item))
    item.SetValue(20);
```

行为要点：

- `GetValue` 先查缓存，再查 Provider；未设置时返回默认值。
- `SetValue` 支持预览事件（可取消/替换）、缓存去重、强制新值、绕过缓存。
- `Reset` 删除键并恢复默认值；`IsDefault` 判断是否未设置。
- 值实现 `INotifyPropertyChanged` / `INotifyCollectionChanged` 时，内容变化会自动回写。
- 配置损坏时备份为 `.failbackup`，并尝试 `.bak` 回退；初始化失败会记录到内部失败列表。

### 3.4 迁移

`ConfigMigration` 在配置服务启动时按版本号执行迁移逻辑，保证旧版本键值可继续使用。新增配置项时保留旧键名是常见做法（例如 `ToolDownloadThread`）。

## 4. 事件总线

`PCL.Core/App/EventBus` 提供进程内异步事件分发：

```csharp
public sealed class MyEvent : EventDataBase { ... }

public sealed class MyHandler : IEventHandler<MyEvent>
{
    public Task HandleAsync(MyEvent data) => Task.CompletedTask;
}

EventBusService.Subscribe<MyEvent>(new MyHandler());
await EventBusService.PublishAsync(new MyEvent());
```

要点：

- `EventBusService` 是生命周期服务，维护通道（channel）与订阅表。
- `EventDataBase` 定义事件基类与元数据。
- `IEventHandler<TEvent>` 定义处理接口；`IResponsibleEventHandler<TEvent>` 支持返回处理结果。
- `AddChannel/RemoveChannel` 用于隔离不同模块的事件域。
- 发布是异步的，处理器异常会被捕获并记录，不影响其他订阅者。

适用场景：跨模块解耦通知（下载完成、实例切换、配置变更等）。

## 5. 日志系统

### 5.1 结构

- `LogLevel`：`Trace/Debug/Info/Warning/Error/Fatal`。
- `ActionLevel`：面向用户的操作级别（如 `MsgBoxFatal`）。
- `LogEntry`：结构化日志条目（时间、级别、线程、模块、消息、异常）。
- `Logger`：实例化日志器，支持作用域与结构化字段。
- `LogWrapper`：为业务代码提供统一的 `LogWrapper.Info(...)` 等静态入口。
- `LogService`：生命周期服务，负责初始化日志、文件轮转、配置联动。
- `LoggerAdapter` / `LoggerFactoryAdapter`：桥接 `Microsoft.Extensions.Logging`。
- `ExceptionDetails`：异常展开与格式化。

### 5.2 行为

- 日志文件位于 `Paths.Data/Log`（按日期/大小滚动）。
- 日志级别受配置 `Config.Debug.Enabled`、启动参数与环境变量控制。
- 致命错误会同时写入日志并弹出对话框。
- 调试构建下会输出更详细的生命周期与调度信息。
- 业务代码不应使用 `Console.WriteLine`；统一使用 `LogWrapper` / `Logger`。

## 6. Essentials 应用服务

| 服务 | 状态 | 职责 |
|---|---|---|
| `ApplicationService` | `BeforeLoading`（最低优先级） | 创建并运行 Avalonia 应用宿主，暴露 `CurrentApplication` |
| `SingleInstanceService` | `BeforeLoading`（最高优先级） | 通过 `instance.lock` 文件锁 + 命名管道转发参数，保证单实例 |
| `PromoteService` | `BeforeLoading` | 需要时提权启动 |
| `MainWindowService` | `Loading` | 创建主窗体并挂接 `WindowContext` |
| `StartupService` | `Running` | 启动后的延迟任务 |
| `UpdateService` / `UpdateHelper` | `Running` | 检查更新、准备更新、退出后替换 |
| `RpcService` / `RpcFunction` / `RpcProperty` | `Loaded` | 本地 RPC（命名管道），供单实例转发与外部调用 |
| `TelemetryService` | `Running` | 可选遥测（默认关闭） |
| `BuildProvenance` | 静态 | 构建来源信息 |

`SingleInstanceService` 细节：

- 主锁：`Paths.SharedLocalData/instance.lock`；备用锁：`Paths.Temp/instance.lock`。
- 检测到重复实例时，通过 `RpcService.PipePrefix@{pid}` 命名管道把命令行转发给已有实例，然后退出。
- 管道使用 `PipeComm.PipeEncoding` 与 `PipeComm.PipeEndingChar`。

## 7. 数据库与 CLI

### 7.1 Database

- `DatabaseService` 基于 LiteDB，缓存连接，按需创建集合。
- `DatabaseEntry` 提供文档基类/时间戳等通用字段。
- 生命周期停止时释放数据库连接。
- 本地缓存另有一套 SQLite 体系（见 [04-IO-网络-存储与工具.md](04-IO-网络-存储与工具.md)）。

### 7.2 CLI

`PCL.Core/App/Cli` 提供轻量命令解析：

- `CommandLine`：命令 + 子命令 + 参数字典。
- `SubcommandDefinition`、`CommandArgument`：参数定义与值。
- `ArgumentValueKind`：`Bool/Text/Decimal` 等。
- `BoolArgument`、`TextArgument`、`DecimalArgument`：强类型参数。
- `CommandArgument.TryCastValue/CastValue` 负责字符串到目标类型的转换。

`PCL.Launcher/Composition/StartupCommandHandler` 在软件启动早期消费这些命令（例如打开特定页面、执行维护操作）。

## 8. 本地化

### 8.1 核心类型

| 类型 | 职责 |
|---|---|
| `Lang` | 全局静态入口：`Lang.Text(key)`、当前语言、语言切换事件 |
| `LocalizationService` | 生命周期服务，加载语言资源、管理字体配置 |
| `LocalizationLanguage` | 语言元数据（代码、显示名、字体） |
| `LocalizationSource` | 资源来源（内嵌/文件） |
| `LocalizationFontProfile` | 不同语言的字体回退配置 |
| `LocalizedPropertyAttribute` | 源生成器生成“随语言变化重新求值”的属性 |

### 8.2 资源与求值

- 语言文件：`PCL.Localization/Languages/*.axaml`，以 `x:Key` 组织键值。
- UI 层通过 `PCL.Core.UI/Localization/LocalizationBackend` 读取 Avalonia 资源。
- `Lang.Text("Key")` 缺键时返回键名并记录警告（便于发现漏翻）。
- 语言切换会触发 `Lang.LanguageChanged`，界面通过 `LocExtension` 或本地化属性自动刷新。
- 若文本包含动态参数，使用格式化 API，而不是字符串拼接。

### 8.3 语言列表

`LocalizationCatalog` 从程序集资源枚举语言：`en-GB`、`en-US`、`es-ES`、`fr-FR`、`ja-JP`、`zh-CN`、`zh-TW`。该类型不依赖 Avalonia，测试可直接用它校验键完整性。

## 9. 全局状态与工具

### 9.1 `States.cs`

保存少量进程级状态（如当前语言），避免散落的静态字段。业务状态（当前实例）放在 `PCL.Launcher.Core/LauncherState`。

### 9.2 `Basics.cs`

`Basics` 是历史悠久的静态工具集合，包含：

- `RunInNewThread` / `RunInNewThreadAsync`：后台线程封装与异常处理。
- `GetMetadata`：读取内嵌 `metadata.json`。
- `GetVersion` / 版本显示名。
- `ExecutablePath`、`ProcessPath`、命令行参数。
- `OpenPath` / `OpenFile`：交给平台层打开。
- `GetResourceStream` / `GetImageUrl`：访问内嵌资源与图片。
- `GetThreadContext` 等诊断辅助。

### 9.3 `Paths.cs`

全局路径解析（见 [01-架构总览.md](01-架构总览.md) 第 7 节）：

- 支持环境变量覆盖（`PCL_DATA_DIR`、`PCL_MINECRAFT_DIR` 等）。
- 自动识别便携/打包形态。
- 自动创建目录并处理旧目录迁移。
- 提供 `SharedData`、`SharedLocalData`、`Temp` 等。

### 9.4 `Secrets.cs`

集中读取敏感与可配置项：

- `PCL_MS_CLIENT_ID`、`PCL_CURSEFORGE_API_KEY`
- `PCL_SENTRY_DSN`、`PCL_TELEMETRY_KEY`
- `PCL_NAID_*`、`PCL_LINK_SERVER_ROOT`、`PCL_LOBBY_DEFAULT_SECRET`
- `PCL_GITHUB_SHA`

避免在源码中硬编码密钥；发布流水线通过环境变量注入。

### 9.5 `Metadata.cs`

定义 `LauncherVersionModel`、`ThirdPartyLicenseModel`、`MetadataModel`，用于“关于”页面、更新检查与许可证展示。

## 10. ViewModel 基础设施

`PCL.Core/ViewModel`：

- `ViewModelBase`：`ObservableObject` 基础上增加生命周期、日志、导航、本地化能力。
- `AsyncState` / `AsyncState<T>`：异步加载状态（未开始/进行中/成功/失败）。
- `LocalizedObservableObject`：语言变化时批量刷新本地化属性。
- 与 `CommunityToolkit.Mvvm` 的 `[ObservableProperty]`、`[RelayCommand]` 配合使用。

这一层不依赖 Avalonia，因此可以被 `PCL.Core.UI` 和 `PCL.Launcher` 共同使用。

## 11. 小结

`PCL.Core/App` 的核心价值是：

1. 用生命周期解决“启动顺序”；
2. 用 DI 解决“依赖构造”；
3. 用声明式配置解决“持久化与观察”；
4. 用日志/事件/数据库/CLI/本地化提供统一横切能力。

理解这四件事，后续阅读业务层与界面层会顺畅很多。
